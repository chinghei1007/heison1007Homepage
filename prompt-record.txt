I’d use **CKEditor for writing, with a small set of visual components for galleries and special layouts**. You would edit everything visually, while the site controls the styling.

Your `[table style=...]` / `[grid]` idea is usually called **shortcodes**. It works, but I wouldn’t make manually typing those the main authoring experience.

| Approach | Writing experience | Main trade-off |
|---|---|---|
| Unrestricted CKEditor | Format everything through toolbar controls | Posts can gradually develop inconsistent styling |
| Text + shortcodes | Type instructions such as `[gallery id="12"]` | Harder to preview; syntax errors and nesting become awkward |
| **CKEditor + controlled components** | Write normally; insert galleries or panels with buttons | Requires some custom editor integration |

**For your site, I recommend the third option.**

For ordinary content, CKEditor would handle paragraphs, headings, bold/italic, links, lists, quotations, code blocks, and comparison tables.

For specialised content, the toolbar would offer actions such as:

- **Insert gallery:** choose a saved gallery, layout, and caption visibility.
- **Insert image:** choose from your media library and select normal or wide display.
- **Insert callout:** choose note, listening impression, or technical explanation.
- **Insert project reference:** choose an existing project to display as a card.

CKEditor supports custom widgets that participate in its editing model, so these can appear as selectable visual objects within the article. They do require development; a gallery picker connected to your database is something we would build. [CKEditor custom components](https://ckeditor.com/docs/ckeditor5/latest/features/custom-components.html)

For example, inserting a gallery could show:

```text
Gallery:        [ Calligraphy practice — September ▾ ]
Layout:         [ Two columns ▾ ]
Spacing:        [ Standard ▾ ]
Image display:  [ Show complete image ▾ ]
Captions:       [ On ]

                  [ Insert gallery ]
```

You see the gallery in the editor. Internally, the content stores its gallery reference and selected options.

**The important distinction is choosing a style versus defining a style.**

You should be able to choose:

```text
Table appearance:  Standard / Compact / Comparison
Gallery layout:    Single / Two columns / Three columns
Content width:     Reading / Wide
Callout appearance: Neutral / Emphasised
```

The design system decides the actual padding, borders, colours, and responsive behaviour. CKEditor also supports predefined styles, which fits this approach. [CKEditor styles](https://ckeditor.com/docs/ckeditor5/latest/features/style.html)

I would avoid authoring things like:

```text
[table style="padding:17px; border-radius:13px; color:#777"]
```

Those values become embedded in individual posts and make future redesigns harder. If we support shortcodes later, they should express intent:

```text
[gallery id="12" layout="two-column" spacing="compact"]
```

That could be an optional writing shortcut which converts into the same visual gallery component.

**Tables and grids should have different jobs.** Use a table for comparing IEM specifications or DAC features. Use a gallery/grid component for arranging artwork, photos, or project cards. On mobile, the gallery can stack while the comparison table gets its own suitable overflow behaviour.

For storage, I’d initially use **CKEditor’s HTML output with explicitly supported custom elements or attributes**, rather than build a second, parallel article format. Media and galleries remain separate database records referenced by the article. Custom widgets need proper save/load conversion, and the backend should validate and sanitise the allowed markup while preserving those references. CKEditor’s internal editing model is distinct from its HTML input/output. [CKEditor widget tutorial](https://ckeditor.com/docs/ckeditor5/latest/framework/tutorials/widgets/implementing-a-block-widget.html)

Finally, CKEditor would edit **the article body**. Title, author, publication date, tags, comments toggle, and project URLs remain normal CMS fields. Homepage sections and post-list layouts remain shared site templates.

That gives you one comfortable writing surface, reusable visual components, and the consistent styling you want across all three sections.

Most of your requirements fit together well. The main constraint is **Spring Boot hosting on a strictly free Cloudflare setup**.

**The editor → API → database flow**

For CKEditor, I would use this flow:

```mermaid
flowchart TD
    A["CMS: title, category, dates, settings"] --> C["Save request"]
    B["Embedded CKEditor: article body"] -->|"HTML output"| C
    C --> D["API: authenticate and validate"]

    E --> F["Extract plain text for search"]
    E --> G[("D1: article HTML and metadata")]
    F --> H[("D1: search index")]
    G --> I["Public page rendered with shared styles"]
```

The browser sends a JSON request containing the editor’s HTML output alongside fields such as title, category IDs, and publication status.

**The server should do the authoritative processing.** Browser-side checks are useful for immediate feedback, but the API should:

- Validate the post fields and permitted content elements.
- Remove unsafe markup and unsupported inline styling.
- Preserve approved component attributes, such as gallery IDs and layout presets.
- Check referenced media and galleries exist.
- Extract searchable text from the cleaned content.
- Save the content and update its search index consistently.

We would keep the sanitised HTML as the editable article source, including the supported widget markup. When reopening a post, that content goes back into CKEditor. The editor and server must agree on the allowed markup so saving doesn’t accidentally destroy a gallery or table.

The public website **doesn’t need to load CKEditor**. It displays the saved content through your shared article styles and gallery components.

One cost-related detail: CKEditor’s self-hosted open-source distribution uses GPL licensing. It also currently offers a limited free commercial CDN plan. If those conditions don’t suit this project, Tiptap’s MIT-licensed open-source core is an alternative, although it requires more work on the editing interface. [CKEditor licensing](https://ckeditor.com/docs/ckeditor5/latest/getting-started/licensing/license-key-and-activation.html), [Tiptap overview](https://tiptap.dev/docs/editor/getting-started/overview)

**Spring Boot and a £0 Cloudflare bill**

Cloudflare Containers currently requires the **Workers Paid plan, starting at US$5/month**, with container usage allowances and additional usage charges. It is not available as a free-plan runtime. My previous answer should have made this distinction explicit. [Cloudflare Containers pricing](https://developers.cloudflare.com/containers/platform/pricing/)

Also, **D1’s 500 MB is database storage, not application memory**. It doesn’t determine whether Spring Boot can run.

The current D1 free limits include:

| Resource | Free allowance |
|---|---:|
| Maximum size of one database | 500 MB |
| Total database storage per account | 5 GB |
| Rows read | 5 million/day |
| Rows written | 100,000/day |

Images hosted on Postimages won’t consume D1 storage beyond their links and metadata. Search indexes and article revisions will consume storage. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

You have three realistic paths:

| Approach | Where Spring Boot runs | Trade-off |
|---|---|---|
| **Everything on Cloudflare Free** | It doesn’t; use a Workers-compatible API | Simplest infrastructure |
| **Cloudflare frontend + external Spring Boot** | Another hosting provider | Keeps Java, adds a deployment and possible cold starts |
| **Local Spring Boot publishing tool** | Your computer, while editing/publishing | No hosted Java service, but CMS isn’t available everywhere |

For the second option, Render’s free web services are a candidate for a containerised Spring Boot app. They sleep after 15 minutes without incoming traffic, and the filesystem is ephemeral. We would need to check the app’s memory usage and startup behaviour before choosing it. [Render free hosting](https://render.com/docs/free)

D1 also isn’t a normal remote SQLite/JDBC connection for Spring Boot. External services access it through HTTP, either through D1’s REST API or a small Worker API we build. That means a custom data-access layer rather than assuming ordinary Spring Data JPA will work unchanged. [D1 access methods](https://developers.cloudflare.com/d1/best-practices/query-d1/)

**My recommendation:** if zero hosting cost and simplicity come first, use a small Workers API with D1. If learning or using Spring Boot is a major purpose of the project, keep it externally hosted and accept the extra integration. Wrangler will deploy the Cloudflare portion; it won’t deploy an external Spring Boot service.

Yes—the entire CMS CRUD flow can be implemented through Spring Boot on Render, with Spring Boot reading and writing Cloudflare D1.

## CRUD architecture

```text
CMS on Cloudflare
      │ authenticated JSON requests
      ▼
Spring Boot on Render
      │ Cloudflare D1 HTTP API + private API token
      ▼
Cloudflare D1
```

Spring Boot would own:

- Authentication and authorization
- Creating and updating posts
- Drafts and autosave
- Revisions
- Publishing and unpublishing
- Categories, media, galleries, and themes
- Import/export
- Input validation and HTML sanitization
- Optimistic-concurrency checks

D1 provides an authenticated HTTP query endpoint with both read and write permissions, so Spring Boot does not need a JDBC connection. It can issue parameterized SQL requests and batches through that endpoint. The Cloudflare credential remains a Render secret and must never reach the CMS browser. [Cloudflare’s D1 Query API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/) explicitly supports SQL, parameters, batches, and D1 Write authorization.

I would implement a `D1Repository` layer in Spring Boot rather than allowing controllers to send arbitrary SQL:

```text
PostController
    ↓
PostService
    ↓
PostRepository interface
    ├── D1PostRepository       production
    └── SQLitePostRepository   local-deployment branch
```

One important limitation is that Render’s free services currently spin down after inactivity. This is acceptable for CMS editing—with an honest “Connecting to the editor service…” state—but not for serving public pages. [Render documents the free-service spin-down behavior](https://render.com/docs/your-first-deploy).

## Your HTML-controller interpretation

Your interpretation is correct. A public request can work like this:

```text
GET /en/posts/my-post
        ↓
Cloudflare route/controller
        ↓
Find published post in D1
        ↓
Not found? Render the 404 template
Found? Select the post template
        ↓
Render React components to HTML
        ↓
Return complete HTML
```

Conceptually, that is the same pattern as a Spring MVC controller with Thymeleaf:

```java
@GetMapping("/posts/{slug}")
String post(@PathVariable String slug, Model model) {
    Post post = repository.findPublishedBySlug(slug);
    model.addAttribute("post", post);
    return "post";
}
```

For this project, though, that controller should run in a Cloudflare Worker rather than Spring Boot. The Worker can query D1 through a native binding and render the React page on the server. Cloudflare’s Vite integration officially supports React Router and server-side rendering. [Cloudflare Vite plugin documentation](https://developers.cloudflare.com/workers/vite-plugin/)

That gives us:

- Complete HTML in the first response
- Good search-engine and link-preview content
- No visible empty page while React fetches the article
- Public pages continue working while Render is asleep
- React hydrates afterward to provide theme switching, gallery lightboxes, search filters, and navigation

Cloudflare also states that bindings are better-performing and less restricted than REST access for applications running inside Workers. Thus, the Worker should use a D1 binding, while external Spring Boot uses the D1 HTTP API. [Cloudflare bindings documentation](https://developers.cloudflare.com/workers/runtime-apis/bindings/)

## What “error state” includes

“Error state” is not one generic screen. Each operation needs an appropriate local state.

For the public website:

- Post not found or unpublished
- Category not found
- Search failed
- Search query is invalid
- Image failed to load
- Gallery is partially unavailable
- Network connection lost
- Public service temporarily unavailable
- Invalid or expired preview link
- Unexpected rendering error

For the CMS:

- Spring Boot is waking up on Render
- Login failed or session expired
- Draft save failed
- Browser is offline
- Autosave retrying
- Another device edited the same revision
- Validation failed
- Publish failed
- Post saved, but public cache refresh failed
- CSV contains invalid or duplicate rows
- Image URL is malformed
- Thumbnail and original image could not be matched
- Some records imported while others failed
- D1 quota or service error

Errors should be placed near the failed item whenever possible. For example, one broken image should show an error on that media card—not replace the entire media library with an error screen.

## Thumbnail import workflow

Yes, the CMS can show thumbnails after CSV import without loading every image simultaneously.

I recommend this workflow:

1. Upload CSV containing names, direct original URLs, and other metadata.
2. CMS parses the CSV locally and shows validation results.
3. CMS asks for an optional bulk paste of Postimages’ **“Thumbnail for websites”** output.
4. CMS parses each `<a>` and `<img>` element.
5. It extracts:
   - `href` → Postimages source-page URL
   - `img.src` → thumbnail URL
   - `img.alt` → proposed name/alt text
6. CMS matches the thumbnails to imported media.
7. A reconciliation screen shows unmatched or ambiguous records.
8. You confirm the import.
9. Records are saved to D1 in bounded chunks.

The media fields should therefore include:

```text
directImageUrl     original/publication image
thumbnailUrl       smaller CMS/list preview
sourcePageUrl      Postimages page
displayName
altText
caption
```

## Preventing excessive image requests

The media library should not create hundreds of requests immediately. I would use:

- Pagination or virtualized scrolling
- Approximately 25–50 media records per page
- Native lazy loading
- Images loaded only as their cards approach the viewport
- A small concurrency limit, such as 4–6 active image loads
- Cancelled requests when cards leave the current view
- “Load more” retry for failed previews
- Import/save operations processed in chunks
- No server-side image download during ordinary CSV parsing

Most preview image requests go directly from the browser to Postimages. The CMS backend does not need to proxy them.

Your example has this structure:


That is Markdown embedded inside HTML. The importer can attempt to clean that up, but normal Postimages HTML is preferable.

## HTML or BBCode?

I strongly prefer the `<a href>` HTML version.

It is clearer for this application because:

- HTML has a standard parser.
- `href`, `src`, and `alt` have precise meanings.
- We can sanitize it safely without executing it.
- It is easier to produce useful row-level validation errors.
- It avoids maintaining a special BBCode parser.
- It matches React/web terminology.

The CMS should accept the bulk HTML only as import input. It should parse the values and discard the markup—it should never store or render the pasted HTML directly.

My preferred final workflow is therefore:

```text
CSV with original direct URLs
             +
Bulk “Thumbnail for websites” HTML
             ↓
Parse and reconcile
             ↓
Preview a lazy-loaded thumbnail grid
             ↓
Edit metadata and resolve mismatches
             ↓
Import into D1 in chunks
```

This is cleaner than prompting you separately for every thumbnail and still gives you control before anything is committed.
