# Personal Homepage and CMS Investigation

This project investigates how to build a custom content management system and personal publishing website with Spring Boot, React, Vite, Render, Cloudflare, Cloudflare D1, and SQLite.

The goal is both practical and educational: produce a usable personal homepage for calligraphy, audio reviews, and software projects while learning how a Spring Boot application can support a modern React authoring interface, cloud persistence, server-rendered public pages, and a portable local deployment.

## Project status

The project is currently in the requirements and architecture stage. Implementation, infrastructure provisioning, and deployment have not started.

The detailed product baseline is in [requirements.md](requirements.md). Early implementation decisions, error states, and the proposed media-import workflow are in [initial-notes.md](initial-notes.md).

## What the project explores

- Building an owner-focused CMS rather than adopting a packaged CMS product
- Serving a React/Vite CMS from Spring Boot's embedded web server
- Hosting the CMS and editorial API as one Spring Boot service on Render
- Performing authenticated CRUD operations against Cloudflare D1 through its HTTP API
- Rendering meaningful public HTML through React and a Cloudflare Worker
- Keeping public reading available while a free Render service is asleep
- Using a shared content model across cloud D1 and local SQLite deployments
- Supporting bilingual English and Traditional Chinese content
- Implementing drafts, autosave, revisions, preview, and explicit publication
- Managing externally hosted Postimages media and reusable galleries
- Testing import/export and local-to-cloud publishing workflows

## Proposed cloud architecture

```text
Owner browser
    -> Spring Boot on Render
       -> serves the compiled React/Vite CMS
       -> exposes the authenticated editorial API
       -> reads and writes D1 through the Cloudflare D1 HTTP API

Public reader
    -> React public site on Cloudflare
       -> Cloudflare Worker performs routing and server rendering
       -> Worker reads published content through a D1 binding
       -> browser displays images delivered by Postimages
```

The public website and CMS intentionally have different availability requirements. The owner-only CMS may encounter a Render free-tier cold start. Public pages must not depend on Render being awake, so public reads and server rendering remain on Cloudflare.

## CMS and Spring Boot

Spring Boot is not only an API process. Its embedded Tomcat server can serve the production files generated by Vite as well as Spring controllers under `/api/**`.

The proposed production build is:

1. Build the React/Vite CMS.
2. Include the generated static assets in the Spring Boot application.
3. Deploy the combined application as one Render web service.
4. Use same-origin sessions and API calls for the CMS.
5. Keep the D1 API token in Render secrets and out of all browser bundles.

Spring Boot owns authentication, validation, sanitisation, drafts, revisions, publication, imports, exports, and all editorial database writes. Browser code never communicates directly with D1.

## D1 and SQLite

Cloudflare D1 uses SQLite semantics but is not a remotely mounted SQLite file and is not a conventional JDBC database. The production Spring Boot application accesses D1 through Cloudflare's authenticated HTTP API.

Persistence should remain behind repository interfaces so the same business rules can use different adapters:

```text
Application service
    -> repository interface
       -> D1 HTTP repository for cloud deployment
       -> SQLite repository for local deployment
```

The local-deployment branch will use a persistent local SQLite database. Cloud and local databases remain independent; import/export and authenticated publishing provide deliberate transfer instead of silent synchronization.

## Public HTML rendering

Public routes should return meaningful HTML in the initial response. A Cloudflare Worker acts like a web controller:

1. Match the locale and route.
2. Look up the published record in D1.
3. Select the appropriate React page template.
4. Render the page to HTML.
5. Hydrate optional browser interactions after delivery.

This supports search engines, link previews, accessibility, and useful first rendering without waiting for a browser-only article fetch.

## Media approach

Image files are uploaded manually to Postimages. The CMS stores references and metadata rather than image binaries.

The planned media workflow supports:

- Direct original-image URLs
- Optional Postimages page and thumbnail URLs
- CSV metadata import
- Optional bulk parsing of Postimages "Thumbnail for websites" HTML
- Lazy-loaded, concurrency-limited preview grids
- English and Chinese names, alt text, and captions
- Ordered, reusable galleries
- Stable media references so a corrected URL updates every use

Automatic Postimages upload and account synchronization are outside the initial scope.

## Main product capabilities

- Public homepage, category pages, articles, project pages, About page, and search
- Responsive owner CMS for desktop, tablet, and phone
- Dynamic categories, tags, brands, and equipment types
- Bilingual content and interface text
- Draft autosave with optimistic concurrency
- Immutable revision checkpoints
- Private preview and explicit publish/unpublish operations
- CMS-managed themes and persistent reader preferences
- Postimages media library and gallery management
- Portable content import/export
- Separate cloud and local deployment profiles

## Intended repository structure

The final structure will be selected during implementation. A likely organization is:

```text
apps/
  cms/                 React/Vite owner interface
  public-site/         React public rendering application
  editorial-api/       Spring Boot application
workers/
  public-read/         Published-only D1 reads and rendering integration
packages/
  contracts/           Versioned API contracts and shared schemas
  design-system/       Shared tokens and React components
  content-renderer/    Approved article component rendering
database/
  migrations/          D1/SQLite-compatible migrations
  fixtures/            Search and acceptance-test fixtures
docs/                  Deployment and operational documentation
```

This is a proposed direction, not yet a committed scaffold.

## Planned implementation stages

1. Prove Spring Boot deployment on Render, D1 HTTP access, local SQLite access, authentication, React/Vite packaging, and public React server rendering.
2. Build the schema and complete the CMS editorial loop: media, authoring, autosave, revisions, preview, publication, and published-only reads.
3. Build the public experience, bilingual search, taxonomy management, themes, accessibility, and responsive layouts.
4. Finish import/export, local deployment, backup/restore, operational documentation, and acceptance verification.

## Cost direction

The baseline targets free Cloudflare services and a free external Spring Boot host where practical. Provider pricing and limits must be rechecked before deployment. The project must not silently enable paid infrastructure or imply guaranteed always-on CMS availability on a free Render service.
